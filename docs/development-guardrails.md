作成日：2026-07-15  
対象：独立OVEウォレット開発チーム／Claude Code  
位置付け：今後の実装判断、レビュー、外部システム連携に使用する基準文書

# 1. この文書の目的

OVEウォレットは、戦国パスポート内の一機能ではなく、戦国経済圏全体から利用される独立サービスとして開発する。

今後、以下のシステムとの連携が増えても、OVE残高、取引履歴、本人識別、代理店紹介関係が矛盾しないように、本書をウォレット側の開発基準とする。

- 代理店システム
- ショッピングカート
- 戦国パスポート
- AIアート教室
- 戦国ガチャ
- NFTマーケット
- メタバース
- 将来の報酬計算エンジン
- 将来のブロックチェーン基盤

本書の目的は、新機能を増やすことではなく、既存実装を壊さず、各システムの責任範囲を維持しながら拡張することである。

---

# 2. 現在の前提

現在のOVEウォレットには、すでに以下の基盤が存在する。

- OVEアカウントとウォレットの自動作成
- CREDIT／DEBIT／REVERSAL／HOLD／RELEASEの台帳処理
- idempotency keyによる二重実行防止
- 行ロックによる同時更新対策
- 残高整合性チェック
- メールOTP認証
- LINEログインのモック実装
- 戦国パスポートSSOのモック実装
- OVE独自セッション
- 外部サービス用HMAC認証
- `service_integrations`による連携先管理
- `account_links`による外部サービスID連携
- 管理画面
- 監査ログ
- APIアクセスログ
- 高額操作の二段階承認
- 管理者MFA

したがって、今後の実装では、新しいアカウント基盤、残高テーブル、取引台帳を別に作らず、現在の構造を拡張する。

# 3. 最上位の設計原則

## 3.1 正式な管理元を分ける

| 情報 | 正式な管理元 |
|---|---|
| OVEアカウント | OVEウォレット |
| OVEウォレット口座 | OVEウォレット |
| OVE残高 | OVEウォレット |
| OVE取引履歴 | OVEウォレット |
| ウォレット利用規約同意 | OVEウォレット |
| 代理店ID | 代理店システム |
| 代理店階層 | 代理店システム |
| 代理店ランク | 代理店システム |
| 顧客と代理店の紹介関係 | 代理店システム |
| 商品・注文・決済 | 各販売システム |
| 販売実績 | 販売実績台帳または専用連携モジュール |
| 報酬額の計算 | 将来の報酬計算エンジン |
| 確定報酬のOVE反映 | OVEウォレット |
| オンチェーン残高 | 将来のブロックチェーン基盤 |

ウォレット側が、代理店階層、紹介代理店の変更、商品別報酬率、上位配分を独自に決定してはならない。

## 3.2 ウォレットは台帳の正本である

OVE残高の正式な根拠は、画面表示用残高ではなく取引台帳とする。

```text
OVE残高
＝ COMPLETEDのCREDIT合計
－ COMPLETEDのDEBIT合計
－ 利用不可として確保された残高
```

残高列は高速表示用の集計値として保持できるが、台帳と不一致になった場合は台帳を優先する。

## 3.3 現在のOVEとオンチェーンOVEを分ける

現段階のOVEは、システム内で管理されるオフチェーン残高である。

以下を混同しない。

- オフチェーン台帳残高
- オンチェーン残高
- 外部ウォレットアドレス
- ブロックチェーン取引ID
- 移行対象残高
- 移行済み残高

外部ウォレットアドレスが登録されても、現在のOVE残高が自動的にオンチェーン資産になるわけではない。

# 4. ID設計の留意事項

## 4.1 OVE_ACCOUNT_IDを基準とする

現在のOVEアカウントを本人識別の中心とする。

```text
OVE_ACCOUNT_ID
＝ OVEウォレット内で本人を識別する不変ID

OVE_WALLET_ID
＝ OVE口座を識別するID
```

LINEユーザーID、メールアドレス、電話番号、戦国パスポート会員ID、代理店システム顧客IDを、OVEの主キーとして使用しない。

## 4.2 common_user_idを無条件に追加しない

全サービス共通IDが別システムですでに発行されている場合は、そのIDをOVEアカウントへ外部IDとして紐づける。

共通ID基盤がまだ存在しない場合は、`OVE_ACCOUNT_ID`を当面の共通本人IDとして利用するか、用途を明確にした`platform_user_id`を追加する。

次の状態は禁止する。

```text
OVE_ACCOUNT_ID
common_user_id
platform_user_id
戦国パスポート会員ID
代理店システム顧客ID
```

これらがすべて「正式な本人ID」として並立する状態を作らない。

## 4.3 外部サービスIDはaccount_linksで管理する

以下の組み合わせを原則一意とする。

```text
service_integration_id + external_user_id
```

例：

```text
SENGOKU_PASSPORT / SGK-000123
AIART / ART-000456
AGENCY_SYSTEM / CUSTOMER-000789
```

同じ外部サービスの同じユーザーIDを、複数のOVEアカウントへ紐づけない。

## 4.4 氏名だけで統合しない

重複アカウントの自動統合に、氏名、LINE表示名、住所だけを使用しない。

統合は、検証済みの認証情報または外部サービスIDを基準にし、管理者承認と監査ログを残す。

# 5. 代理店紹介連携の留意事項

## 5.1 紹介関係の正本は代理店システム

ウォレット側は、紹介代理店を独自に決定、変更、上書きしない。

ウォレット側に保存するのは、連携結果を確認するための最小限の参照情報とする。

例：

- `referral_relation_id`
- `agency_id`
- `relation_status`
- `linked_at`
- `last_synced_at`
- `sync_status`

代理店階層、代理店ランク、上位者一覧をウォレットへ恒久複製しない。

## 5.2 紹介関係はウォレットではなくアカウントへ紐づける

紹介関係は「口座」ではなく「本人」に対する関係として扱う。

原則として以下へ紐づける。

```text
agency_referral_links.ove_account_id
```

将来1人が複数種類のウォレットを持っても、紹介代理店との関係がウォレットごとに重複しないようにする。

## 5.3 代理店IDをURLに直接出さない

代理店専用URLでは、代理店IDを直接指定せず、代理店システムが発行する署名付き紹介トークンを使用する。

```text
https://wallet.example.jp/register?ref_token=xxxxx
```

ウォレット側は、`ref_token`を検証せずに代理店を確定しない。

## 5.4 ref_tokenをURLに残さない

推奨処理：

```text
1. ref_token付きURLへアクセス
2. サーバーでトークンを受領
3. 代理店システムで検証
4. 紹介セッションを作成
5. ref_tokenなしのURLへリダイレクト
6. 認証後は紹介セッションIDを使用
```

追加するHTTP方針：

```text
Referrer-Policy: no-referrer
Cache-Control: no-store
```

分析ツール、アクセスログ、エラー通知へ平文の`ref_token`を送信しない。

## 5.5 紹介トークンと紹介セッションを分ける

紹介トークンは代理店が複数人へ配布できる情報であり、ユーザーの登録処理は個別の一時処理である。

したがって、次を分ける。

```text
referral_token
＝代理店システムが発行する紹介情報

referral_session
＝ウォレット登録者ごとの一時的な登録セッション
```

推奨ステータス：

```text
CREATED
VERIFIED
AUTHENTICATED
SYNC_PENDING
SYNCED
CONFLICT
EXPIRED
FAILED
```

## 5.6 認証を挟んでも紹介情報を維持する

以下を挟んでも紹介情報を失わないこと。

- LINEログイン
- メールOTP
- 戦国パスポートSSO
- ブラウザのリダイレクト
- 利用規約同意
- 一時的な通信エラー

サーバー側紹介セッション、認証用state、短時間Cookieを使用し、クライアントだけに依存しない。

## 5.7 別代理店URLを後から開いた場合

すでに紹介代理店が確定しているユーザーが別の代理店URLを開いても、ウォレット側で関係を変更しない。

代理店システムへ照会し、以下のような結果を受け取る。

```text
CREATED
EXISTING
CONFLICT
REASSIGNMENT_REQUIRED
REJECTED
```

`CONFLICT`または`REASSIGNMENT_REQUIRED`は管理者確認へ送る。

# 6. 登録フローの推奨仕様

```text
1. 代理店専用URLへアクセス
2. ref_tokenを取得
3. 代理店システムでトークン検証
4. referral_sessionを作成
5. URLからref_tokenを除去
6. LINE・メール等で本人認証
7. 既存OVEアカウントを検索
8. OVEアカウントを作成または取得
9. ウォレットを作成または取得
10. 利用規約同意を確認
11. 紹介関係同期イベントを保存
12. 代理店システムへ紹介関係登録を送信
13. 成功時にSYNCED
14. 失敗時に再送対象へ登録
15. 紹介関係確定後に登録特典を付与
```

## 6.1 紹介URLなしの新規登録

紹介URLがない新規ユーザーを完全拒否するのではなく、以下の保留状態を推奨する。

```text
アカウント：PENDINGまたはRESTRICTED
紹介状態：REFERRAL_REQUIRED
```

この状態では次を制限する。

- 登録特典3,000 OVE
- OVE利用
- 紹介キャンペーン特典
- 代理店限定機能
- 将来のオンチェーン移行

## 6.2 既存ユーザー

すでに代理店システムで紹介関係が確定している既存ユーザーは、紹介URLなしでも既存関係を照会し、ウォレットを作成できるようにする。

重複する紹介関係を新規作成しない。

# 7. 登録特典3,000 OVEの留意事項

登録特典は、戦国パスポートの登録だけに固定せず、独立OVEウォレットの初回有効化特典として整理する。

推奨ルール：

```text
rule_code:
OVE_WALLET_REGISTRATION_BONUS

amount:
3,000 OVE

limit:
同一人物につき1回
```

推奨冪等キー：

```text
WALLET_REGISTRATION_BONUS:{OVE_ACCOUNT_ID}
```

共通IDが正式に決定した場合は、その不変IDを使用する。

## 7.1 付与条件

以下をすべて満たした後に付与する。

1. 本人認証完了
2. 利用規約同意
3. OVEアカウント作成または確認
4. ウォレット作成または確認
5. 重複アカウント確認
6. 紹介トークンまたは既存紹介関係の確認
7. 代理店紹介関係の同期完了、または管理者承認

代理店連携が失敗している場合は、登録特典を保留できるようにする。

## 7.2 メール認証だけの不正取得対策

メールOTPだけで何度もアカウントを作成し、3,000 OVEを取得できないようにする。

登録特典の確定には、以下のいずれかを推奨する。

- LINE認証済み
- 電話番号認証済み
- 既存サービスで本人確認済み
- 管理者確認済み

ウォレット作成と登録特典付与を同じ条件にしない。

---

# 8. AIアート教室参加10,000 OVEの留意事項

AIアート教室参加特典は、予約ではなく実参加確認後に付与する。

冪等キー：

```text
AIART_ATTENDANCE:{EVENT_ID}:{OVE_ACCOUNT_ID}
```

外部サービスから送られた金額を無条件に信用するのではなく、`reward_rules`に登録されたルールと照合する。

ただし、将来報酬計算エンジンから確定済み報酬を受け取るAPIでは、ウォレット側で報酬計算を行わない。

この2種類を区別する。

```text
特典ルール型付与
＝ウォレット側のreward_rulesで条件・金額を管理

確定報酬型付与
＝外部報酬計算エンジンが確定した金額を受領
```

# 9. 外部API連携の留意事項

## 9.1 既存基盤を再利用する

代理店システム、AIアート教室、戦国パスポートなどの連携には、既存の以下を使用する。

- `service_integrations`
- HMAC-SHA256署名
- タイムスタンプ
- nonce
- idempotency key
- APIアクセスログ
- サービス別上限
- 緊急停止機能

新しい認証方式や付与APIを連携先ごとに乱立させない。

## 9.2 既存付与APIを拡張する

将来の代理店報酬のために、既存の付与APIと重複するAPIを新設しない。

既存の`/rewards/grant`相当のAPIを拡張し、以下の取引種別を追加できる構造にする。

```text
AGENCY_COMMISSION
UPLINE_COMMISSION
CASTLE_OWNER_REWARD
ADVISOR_REWARD
CAMPAIGN_COMMISSION
```

ウォレット側では、報酬額、上位配分、ランク条件を再計算しない。

## 9.3 外部サービスに任意のOVE_ACCOUNT_ID照会を許可しない

外部サービスは、自サービスに紐づく`external_user_id`だけを照会できるようにする。

OVE_ACCOUNT_IDを指定すれば誰の残高でも取得できるAPIを本番公開しない。

# 10. 再送・障害対応の留意事項

## 10.1 Transactional Outboxを使用する

ウォレット登録後、代理店システムへの連携ジョブ登録前に障害が起きても、連携予定データを失わないようにする。

OVEアカウント作成、ウォレット作成、紹介状態更新、Outboxイベント作成を同一DBトランザクションで確定する。

推奨テーブル：

```text
integration_outbox

id
event_type
aggregate_type
aggregate_id
destination_service
payload
idempotency_key
status
attempt_count
available_at
locked_at
last_error_code
last_error_message
created_at
processed_at
```

## 10.2 再送仕様

- 自動再送
- 指数バックオフ
- 最大再送回数
- 手動再送
- Dead Letter相当の管理状態
- エラー理由の保存
- 同じイベントの二重登録防止
- タイムアウト後の結果照会

「送信成功したが応答を受信できなかった」場合も、同じ冪等キーで安全に再送できること。

## 10.3 代理店システム停止中

代理店システム停止中でも、本人認証とウォレット口座作成を完了できる構成を推奨する。

ただし、紹介関係が確定するまでは、登録特典や一部利用機能を保留する。

---

# 11. 台帳処理の絶対禁止事項

以下は禁止する。

1. 残高だけを直接UPDATEする
2. COMPLETED取引を削除する
3. COMPLETED取引の金額を変更する
4. 誤付与を履歴削除で修正する
5. idempotency keyなしで外部付与する
6. 残高不足でDEBITを成功させる
7. 外部サービスからOVE DBを直接更新する
8. 代理店報酬をウォレット側で再計算する
9. ブロックチェーン移行時に元台帳を消す
10. アカウント統合時に取引履歴をまとめて上書きする

訂正は必ずREVERSALまたは対応する逆仕訳取引で行う。

# 12. セキュリティ上の留意事項

## 12.1 本番公開前の必須項目

現在の残高照会・取引履歴照会は、本番公開前に本人・管理者・外部サービスでAPIを分離する。

推奨：

```text
ユーザー本人
GET /api/v1/me/wallet
GET /api/v1/me/transactions

管理者
GET /api/v1/admin/wallets/{walletId}

外部サービス
GET /api/v1/service/accounts/{externalUserId}/balance
```

ユーザー本人用APIは、URLでOVE_ACCOUNT_IDを受け取らず、セッションから本人を特定する。

## 12.2 モック認証を本番で使わない

LINEログインと戦国パスポートSSOは、本番実装完了までは準備中表示とする。

```text
NODE_ENV=production
かつ
AUTH_MODE=mock
```

の場合はアプリ起動を失敗させる。

## 12.3 DBレベルの保護

- `ove_transactions`のDELETE禁止
- COMPLETED取引の重要項目UPDATE禁止
- `audit_logs`のUPDATE／DELETE禁止
- アプリ実行DBロールとマイグレーションDBロールの分離

## 12.4 ログへ出してはいけない情報

- 紹介トークン原文
- ワンタイムコード
- IDトークン本文
- APIシークレット
- セッションCookie
- 外部ウォレット秘密鍵
- HMAC署名用シークレット

# 13. Feature Flag

外部連携は、初期状態OFFで段階的に有効化する。

推奨：

```text
ENABLE_PLATFORM_USER_ID
ENABLE_WALLET_REFERRAL_TOKEN
ENABLE_AGENCY_REFERRAL_SYNC
ENABLE_AGENCY_SYNC_RETRY
ENABLE_WALLET_REGISTRATION_BONUS
ENABLE_EXTERNAL_REWARD_TYPES
ENABLE_ONCHAIN_MIGRATION
```

Feature FlagをOFFにした際も、既存のログイン、残高表示、取引履歴、管理画面が壊れないこと。

# 15. 管理画面で追加する機能

## 必須

- `SYNC_PENDING`／`FAILED`／`CONFLICT`の絞り込み

# 16. テスト要件

## 16.1 紹介登録

- 有効な紹介URLから新規登録
- 無効な紹介トークン
- 期限切れ紹介トークン
- 同じ紹介URLから複数人が登録
- LINEログイン後も紹介情報が残る
- メールOTP後も紹介情報が残る
- 既存ユーザーが紹介URLを開く
- 別代理店URLを後から開く

# 22. 開発チームへの最終共有文

OVEウォレットは、OVE残高と取引履歴の正式な管理元です。

代理店ID、代理店階層、顧客と代理店の紹介関係は、既存の代理店システムを正式な管理元とします。ウォレット側で独自に紹介代理店を決定、変更、上書きしてはいけません。

既存のOVEアカウント、ウォレット、取引台帳、外部サービス連携基盤を再利用し、新しい共通ID、残高テーブル、取引台帳を重複して作成しないでください。

代理店専用URLから取得した紹介情報は、安全な紹介セッションへ変換し、認証後も維持します。代理店システムとの連携失敗に備え、冪等性、Transactional Outbox、自動再送、手動再送、監査ログ、Feature Flagを前提に実装してください。

将来の代理店報酬について、ウォレット側は報酬計算を行いません。報酬計算エンジンから受け取った確定済み金額を、既存のOVE台帳へ記録する役割だけを持ちます。

現段階では、オンチェーン化、秘密鍵管理、ユーザー間送金、報酬計算を実装せず、オフチェーン台帳の正確性、本人識別、代理店紹介連携、本番セキュリティを優先してください。
