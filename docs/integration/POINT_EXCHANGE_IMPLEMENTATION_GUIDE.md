# ポイント → ORI 交換（申請制）実装説明書

外部システムで貯まったポイントを、利用者の申請と貴社の承認を経て ORI へ交換するための
実装手順書です。連携システムごとに同じ手順で実装していただけます。

対象読者: 外部システムの開発担当者
前提: 千ノ国 共通イベント（`X-SenNoKuni-*`）の署名鍵を発行済みであること

---

## 1. 役割分担

| | 担当 |
|---|---|
| 申請の受付 | **外部システム** |
| ポイントの確保・減算 | **外部システム** |
| 承認・却下の判断 | **外部システム** |
| ORI の付与 | ウォレット |
| 発行量の上限 | ウォレット |

**申請から承認までの処理は、すべて外部システム側で完結します。** ウォレットは承認後に
送られてくる付与イベントを受けるだけです。

この分担は設計上の都合ではありません。**ポイント残高を持っているのは外部システムだけ**
なので、申請時にそのポイントを押さえられるのも外部システムだけだからです。ウォレット側に
申請を受ける口を作ると、承認を待つ間に同じポイントで何件でも申請できてしまいます。

---

## 2. 全体の流れ

```
利用者                外部システム                      ウォレット
  |                       |                                |
  |--- 交換を申請 ------->|                                |
  |                       |-- ポイントを「確保」            |
  |                       |   (減算ではない)                |
  |<-- 「申請中」を表示 ---|                                |
  |                       |                                |
  |                  [担当者が承認]                         |
  |                       |-- 確保を確定（ポイント減算）     |
  |                       |                                |
  |                       |--- reward.granted ------------->|
  |                       |                                |-- ORI を付与
  |                       |<-- 200 OK ---------------------|
  |<-- 「交換完了」-------|                                |
```

却下した場合は、確保を解除してポイントを戻し、ウォレットへは**何も送りません**。

---

## 3. 外部システム側に実装するもの

### 3.1 申請レコード

申請1件につき1レコードを作り、**申請IDを発番**してください。この申請IDは後で
`event_id` としてウォレットへ送ります（6章）。

### 3.2 ポイントの確保 ← 最重要

**申請を受け付けた時点で、対象ポイントを他の交換に使えない状態にしてください。**

ここを飛ばすと申請制の意味が失われます。

```
【確保しない場合に起きること】
残高 3,000 pt
  → 3,000 pt の交換を申請   … 残高はまだ 3,000 pt
  → もう一度 3,000 pt を申請 … これも通ってしまう
  → 2件とも承認 → 6,000 pt 分の ORI が出る（実際には 3,000 pt しかない）
```

**減算ではなく確保**である点にご注意ください。却下時に戻す必要があるためです。
実装方法は問いません（確保済みフラグ、確保テーブル、残高を「総額」と「利用可能額」に
分けるなど、貴社の設計に合わせてください）。

### 3.3 承認・却下の画面

担当者が申請を一覧で見て、1件ずつ承認・却下できる画面をご用意ください。

| 操作 | ポイント | ウォレットへの送信 |
|---|---|---|
| 承認 | 確保を確定（減算） | `reward.granted` を送信 |
| 却下 | 確保を解除（元に戻す） | **送信しない** |

### 3.4 申請の状態遷移

```
申請中 ──承認──> 送信待ち ──送信成功──> 完了
  │                  │
  │                  └──送信失敗──> 再送待ち ──(再送)──> 完了
  │
  └──却下──> 却下済み（ポイント返却）
```

**「承認済みだが送信に失敗した」状態を必ず持たせてください。** ネットワーク障害や
ウォレット側の一時的な不調で送信が失敗することがあります。この状態を持たずに
「承認＝完了」としてしまうと、ポイントだけ減って ORI が付かない申請が生まれます。

再送は同じ申請IDで行えば安全です（6章）。

### 3.5 利用者向けの表示

承認を待つ時間が発生するため、利用者に「申請中」であることが分かる表示をご用意ください。
確保中のポイントが残高から引かれて見えるのか、別枠で見えるのかも、あわせてご検討ください。

## 4. ウォレットへの送信

### 4.1 エンドポイント

```
POST https://api.sennokuni-wallet.com/api/integrations/events
Content-Type: application/json
```

会員券・NFTコレクションと**同じエンドポイント・同じ署名方式**です。すでに共通イベントを
送信されている場合、新しい接続を作る必要はありません。署名鍵の許可 `event_type` に
`reward.granted` を追加するだけです（8章）。

### 4.2 認証ヘッダー

| ヘッダー | 内容 |
|---|---|
| `X-SenNoKuni-Key-Id` | 発行済みの key_id |
| `X-SenNoKuni-Timestamp` | **UNIXエポック秒（10桁）** |
| `X-SenNoKuni-Nonce` | リクエストごとに変わるランダム文字列 |
| `X-SenNoKuni-Signature` | HMAC-SHA256 の hex（`sha256=` 接頭辞は任意） |
| `Idempotency-Key` | **`event_id` と同じ値**（必須・不一致は 400） |
| `X-Event-Version` | 任意。送る場合は `event_version` と一致必須 |

> **タイムスタンプは「秒」です。** ミリ秒（13桁）を送ると許容ずれ（±5分）を超えて
> 401 になります。外部API（`X-OVE-*`）はミリ秒ですが、こちらは秒です。混同にご注意ください。

### 4.3 署名対象文字列

**改行（LF）区切りの6行**です。

```
key_id
timestamp
nonce
METHOD（大文字）
path（クエリ文字列を含めない）
raw_body
```

`raw_body` は**実際に送信するリクエストボディの文字列そのもの**です。ウォレット側で
再整形や再直列化はしません。したがって JSON のキー順序・インデント・日本語のエスケープ
方式は問いません。守っていただくのは1点だけです。

> **ボディ文字列を1回だけ組み立て、その文字列に署名し、その同じ文字列を送る。**

```js
const rawBody = JSON.stringify(body); // この値を署名にも送信にも使う
const timestamp = String(Math.floor(Date.now() / 1000)); // 秒
const nonce = crypto.randomUUID();
const path = "/api/integrations/events";

const signature = crypto
  .createHmac("sha256", signingSecret)
  .update([keyId, timestamp, nonce, "POST", path, rawBody].join("\n"))
  .digest("hex");

await fetch(`https://api.sennokuni-wallet.com${path}`, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "X-SenNoKuni-Key-Id": keyId,
    "X-SenNoKuni-Timestamp": timestamp,
    "X-SenNoKuni-Nonce": nonce,
    "X-SenNoKuni-Signature": signature,
    "Idempotency-Key": body.event_id,
  },
  body: rawBody, // ここで JSON.stringify(body) を書き直さないこと
});
```

同じ nonce は再利用できません（約5分間、リプレイとして 401）。**再送時は nonce と
timestamp を作り直してください。** `event_id` は変えません。

### 4.4 リクエスト本文

```json
{
  "event_id": "EXCHANGE-2026-000123",
  "event_type": "reward.granted",
  "event_version": "1.0",
  "occurred_at": "2026-09-16T10:00:00.000Z",
  "source_system_key": "<発行時にお伝えした値>",
  "common_user_id": "CU-0001",
  "amount": 3000,
  "product_code": "point_exchange",
  "metadata": {
    "application_id": "EXCHANGE-2026-000123",
    "approved_by": "admin-042",
    "approved_at": "2026-09-16T09:58:00.000Z"
  }
}
```

| 項目 | 必須 | 内容 |
|---|---|---|
| `event_id` | ✓ | **申請IDを入れてください**（6章） |
| `event_type` | ✓ | `reward.granted` 固定 |
| `event_version` | ✓ | `1.0` 固定 |
| `occurred_at` | ✓ | ISO 8601（UTC） |
| `source_system_key` | ✓ | 鍵に登録された値と**一致必須**（不一致は 403） |
| `common_user_id` | ✓ | 共通ユーザーID |
| `amount` | ✓ | **付与する ORI 数。正の整数のみ**（小数・0・負数は 400） |
| `product_code` | — | 上限を分けたい単位（7章） |
| `metadata` | — | 任意。承認者・承認日時などの記録に |

**交換レートはウォレットが持ちません。** 外部システムでレートを適用し、その結果の ORI 数を
`amount` として送ってください。

`metadata` に入れた値は受信本文としてそのまま保全されます。ただしウォレットの取引一覧
画面には表示されません（表示が必要な場合は別途ご相談ください）。

### 4.5 正常応答

```json
{ "ok": true, "event_id": "EXCHANGE-2026-000123", "cached": false, "result": { ... } }
```

`cached: true` は「同じ内容を以前に処理済み」という意味です。**エラーではありません。**
再送が正しく冪等に処理されたことを示します。

## 5. エラーと対処

エラー応答は次の形式です。

```json
{ "ok": false, "error": { "code": "VALIDATION_ERROR", "message": "..." }, "request_id": "..." }
```

`request_id` はお問い合わせの際にお知らせください。調査が早くなります。

| HTTP | code | 原因 | 対処 |
|---|---|---|---|
| 401 | `INVALID_SIGNATURE` | 署名不一致・時刻ずれ・nonce再利用 | **署名対象文字列とタイムスタンプ（秒）を確認**。再送は nonce を作り直す |
| 403 | `FORBIDDEN` | `source_system_key` 不一致、または鍵が `reward.granted` 未許可 | 弊社へご連絡ください |
| 404 | `NOT_FOUND` | その `common_user_id` のウォレットが無い | **再試行可**。利用者がウォレット未登録・未連携の可能性 |
| 400 | `VALIDATION_ERROR` | `amount` が不正、上限超過、付与ルール未登録、共通IDが複数アカウントに紐づく | message で切り分け。上限超過は7章 |
| 409 | `COMMON_USER_ACCOUNT_CONFLICT` | ① 同じ `event_id` で**内容の違う**本文を送信 ② 同じ `event_id` を**同時に**複数回送信 | ①は6章を確認（再送しても直りません）。②は**少し待って再試行** |
| 422 | `UNSUPPORTED_EVENT_VERSION` | `event_version` が不正 | `1.0` を送る |
| 503 | `FEATURE_DISABLED` | 受け口が無効 | 弊社へご連絡ください |

> **409 のコード名にご注意ください。** `COMMON_USER_ACCOUNT_CONFLICT` という名前ですが、
> 実際には**冪等キーの衝突**を表します（共通IDの問題ではありません）。判別は `message` で
> 行ってください。`already processed with a different request body` なら①、
> `currently being processed` なら②です。

**404 は再試行してください。** 利用者がまだウォレットを作っていない、共通IDの連携が
済んでいない、といった時間で解決する状態を含みます。承認済みの申請を「送信失敗」の
まま保持し、後で再送できる設計（3.4節）が効いてきます。

---

## 6. 冪等性と再送

### `event_id` には申請IDを入れてください

ウォレットは `source_system_key` + `event_id` の組で重複を判定します。

| 送信内容 | 結果 |
|---|---|
| 同じ `event_id`・**同じ本文** | 前回の結果を返す。**二重付与しない**（`cached: true`） |
| 同じ `event_id`・**違う本文** | **409 で拒否**。処理しない |
| 違う `event_id` | 別の付与として処理する |

つまり、**申請IDを `event_id` にしておけば、送信の再送も承認ボタンの二度押しも安全**です。
逆に送信のたびに新しいIDを振ると、この保護がまったく効きません。

### 再送時の注意

再送では `event_id` と本文を**1バイトも変えないでください**。`occurred_at` を送信時刻で
作り直したり、`metadata` に送信回数を足したりすると本文が変わり、409 になります。

一方、**`X-SenNoKuni-Nonce` と `X-SenNoKuni-Timestamp` は作り直してください**（同じ
nonce は 401、古い timestamp も 401 になるため）。署名も作り直しになります。

## 7. 上限

ウォレット側に発行量の上限があります。超えると 400 が返ります。

| 上限 | 初期値 | 何を止めるか |
|---|---|---|
| 1回あたり | 100,000 ORI | レート計算ミスによる桁違いの付与 |
| 月あたり合計 | 1,000,000 ORI | 想定外の大量発行 |

**最初は絞った値から始め、実際の流量を見て調整する方針**です。上限に当たった場合は
400 が返るので気づけます。変更をご希望の場合はご連絡ください（管理画面から即時変更でき、
デプロイは不要です）。

`product_code` を分けると**上限も発行量の集計も別々**になります。交換の種別が複数ある場合
（通常交換・キャンペーン交換など）は分けておくと、片方だけ止めることもできます。

## 8. 交換の取消

付与後に取り消す必要が生じた場合は、`reward.reversed` を送ってください。

```json
{
  "event_id": "EXCHANGE-CANCEL-2026-000123",
  "event_type": "reward.reversed",
  "event_version": "1.0",
  "occurred_at": "2026-09-16T11:00:00.000Z",
  "source_system_key": "<発行時にお伝えした値>",
  "original_event_id": "EXCHANGE-2026-000123"
}
```

- `event_id` は**取消操作そのものの新しいID**です（元の申請IDではありません）
- `original_event_id` に**取り消したい付与の `event_id`**（＝元の申請ID）を入れます
- 取り消せるのは、**自システムが付与したもの**だけです

ポイントを戻すかどうかは外部システム側の判断です。ウォレットは ORI を戻すだけです。

## 9. 接続前に弊社側で行う準備

貴社の作業ではありませんが、**未了だと送信がすべて弾かれます。**

| # | 準備 | 未了時の症状 |
|---|---|---|
| 1 | 署名鍵の許可 `event_type` に `reward.granted`（取消も使う場合は `reward.reversed`）を追加 | 403 `FORBIDDEN` |
| 2 | 付与ルールの登録 | 400 `VALIDATION_ERROR` |

### 付与ルールについて

この経路は、**署名鍵さえあれば任意の額を発行できます。** そのため上限のない状態で通すことは
せず、付与ルールの登録を必須にしています。未登録のままだと**すべての付与が 400 で拒否**
されます。

ルールコードは `product_code` から決まります。

```
rule_code = "COMMON_EVENT_REWARD:" + (product_code が無ければ "default")
```

**送信する `product_code` と登録するルールコードが一致していないと拒否されます。**
接続前に `product_code` の値を弊社とすり合わせてください。

## 10. 接続前チェックリスト

**外部システム側**

- [ ] 申請時にポイントを**確保**している（減算ではない）
- [ ] 却下時に確保を解除してポイントを戻している
- [ ] 「承認済み・送信失敗」の状態を持ち、再送できる
- [ ] `event_id` に**申請ID**を使っている
- [ ] 再送時に `event_id` と本文を変えていない
- [ ] 再送時に nonce と timestamp を**作り直している**
- [ ] タイムスタンプが**秒（10桁）**である
- [ ] 署名した文字列と送信した文字列が同一である
- [ ] 404 を再試行対象として扱っている
- [ ] `amount` が正の整数である

**弊社側**

- [ ] 署名鍵の許可 `event_type` を追加
- [ ] `product_code` の値を合意
- [ ] 付与ルールを登録
