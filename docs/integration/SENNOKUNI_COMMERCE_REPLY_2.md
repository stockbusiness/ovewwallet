## 1. `entitlement_type` → **追加対応は不要です**

`membership_pass` のみとのこと、承知しました。**弊社側の変更は発生しません。** そのまま
お送りください。

### 【要対応】`serial_number` を文字列でお送りください

サンプルJSONの `"serial_number": 1` は**数値**になっています。弊社は**文字列のみ**を受け
付けるため、このままですと**エラーにもならず、シリアル番号だけが保存されません。**

```json
"serial_number": 1      ← 保存されません（エラーも出ません）
"serial_number": "1"    ← こちらでお願いします
```

文字列にしている理由は、`"0034"` のような**桁を固定したゼロ埋め表記**を受け取れるように
するためです。先頭の `0` を落とさずそのまま保存します。

気づきにくい挙動で恐縮ですが、**他の項目も同様に文字列で判定しています**ので、
`asset_code` / `name` / `image_url` / `thumbnail_url` / `description` / `rarity` も
文字列でお送りください（サンプルでは問題ありません）。

### `MEMBERSHIP_PASS`（大文字）も元から受け付けております

小文字へ修正いただいた件ですが、**弊社は大文字・小文字の両方を受理する実装**です。

| 送信値 | 結果 |
|---|---|
| `MEMBERSHIP_PASS` | 受理 |
| `membership_pass` | 受理 |

したがって**修正前の大文字でも通っていたはず**です。修正自体に問題はございませんので、
そのまま小文字でお送りいただいて構いません。

念のためですが、**もし大文字で実際にエラーが出ていたのでしたら、原因は別にあります。**
その場合はエラーの内容をお知らせください。切り分けます。

### ご確認: `entitlement_id` の所在

サンプルでは `data` が `{ "...": "(業務項目一式)" }` とプレースホルダのため確認できません
でしたが、**`entitlement_id` は必須**です。これが無いと400になります。

`event_version: "1.0"` でお送りの場合、**`data.entitlement_id` でもトップレベルの
`entitlement_id` でも構いません**（両方ある場合は値が一致している必要があります）。

`entitlement_id` は弊社側で**保有権の一意キー**として使い、再送されても重複して付与され
ないようにしています。商品ごとではなく、**購入1件ごとに一意な値**をお願いします。

### ご確認: `common_user_id` の形式

サンプルの `"cu_00000000001"` は、弊社が正式形式としている **`cu_` + 32桁の小文字16進数**
と異なります。サンプル値とのことですので実データでは問題ないかと存じますが、念のため
ご確認ください。

`event_version: "1.0"` では形式検証をかけていないため**この値でも通ってしまいます**が、
そのIDに対応するウォレットが存在しなければ404になります。将来 `1.1` へ移行される際には
形式検証が有効になりますのでご留意ください（当面 `1.0` のままで結構です）。

## 2. ポイント付与について → **2つは別物で、両方とも有効です**

ご質問の件、**置き換えではありません。** 認証方式から別系統の2つのAPIが並存しています。

| | `POST /api/v1/rewards/grant` | `reward.granted`（共通イベント） |
|---|---|---|
| 認証 | `X-OVE-*` ヘッダー | `X-SenNoKuni-*` ヘッダー |
| 必要なもの | 外部サービス連携の登録＋専用APIキー | **共通イベントの署名鍵（カードと同じ鍵）** |
| 宛先 | `/api/v1/rewards/grant` | `/api/integrations/events` |
| 上限の識別子 | `transaction_type` | `product_code` |

**廃止予定はございません。** どちらでも付与できます。

### 弊社からの推奨：共通イベント（`reward.granted`）

**カード配信と同じ経路・同じ署名鍵で済む**ためです。`/api/v1/rewards/grant` をお使いになる
場合、カードとは**別の認証方式・別の鍵・別の登録**が追加で必要になります。

### 【要確認】`reward_rule_id` について

恐れ入りますが、**`reward_rule_id` というフィールドは弊社の実装に存在しません。**
`/api/v1/rewards/grant` が受け付ける項目は次のとおりです。

```
service_code / external_user_id / event_type / event_id
amount / transaction_type / display_name / idempotency_key
```

また `service_code` は**あらかじめ定義された値からの選択**で、`sengoku-market` という
文字列は使えません。

### 【重要】現在ご送信中かどうかをご確認ください

「現在連携している」とのご記載が気になっております。**弊社の記録では、
`/api/v1/rewards/grant`（`X-OVE-*` 方式）で現在稼働中の連携先はございません。**

もし**実際に送信されている**のでしたら、**2026-09-07に署名の作り方を変更しております**
ので、影響を受けている可能性があります。変更内容は次のとおりです。

> 署名対象の本文を「**実際に送信したバイト列そのもの**」に変更しました。
> 以前は弊社側でJSONを組み立て直した文字列と照合していたため、キー順序や整形の違いで
> 正しい署名でも401になる問題がありました。

**現在401が出ていないか**をご確認いただけますでしょうか。出ている場合は仕様書をお送り
します（契約テスト用の固定データ12ケースもご提供できます）。

一方、まだ**実装・設計の段階**でしたら、上記の推奨どおり共通イベント方式でご検討ください。
その場合 `product_code` の値だけ決めていただければ、こちらで付与ルールを登録します。

来週のご連絡をお待ちしております。

## 5. Secretの受け渡し方法 → **弊社案をご提示します**

**期限付きの共有リンク**を第一案とさせてください。いずれも無料で使え、閲覧後または期限
経過で自動的に失効します。

| 方法 | 備考 |
|---|---|
| **Bitwarden Send**（推奨） | アカウント登録不要で受信可。閲覧回数・有効期限を指定でき、パスワード保護も可能 |
| 1Password で共有 | 同等の機能。貴社でご利用中でしたらこちらでも |
| PGP暗号化 | 双方に鍵がある場合 |

いずれの場合も、次の運用でお願いできればと存じます。

- **リンクと閲覧用パスワードは別経路で**お送りする（リンクはメール、パスワードは電話等）
- 有効期限は**短め（1〜3日）**に設定する
- 受領後、**受信側から受領確認のご連絡**をいただく（その後リンクを失効させます）

貴社にご希望の方法がございましたら、そちらに合わせます。**双方向とも同じ方法**で問題
ありません。
