## 1. 取引照合について → **実装済みです。追加開発は不要です**

ご要望の日次照合の仕組みは、すでに稼働しております。エンドポイントは2本です。

### 1-1. 日次照合用CSV一括ダウンロード

```
GET /api/v1/service/transactions/export
  ?period_from=2026-08-01T00:00:00.000Z
  &period_to=2026-08-31T23:59:59.000Z
  &rule_code=SENGOKU_LEARNING_JOURNEY_REWARD   ← 任意（省略可）
```

CSVの列は、いただいた一覧と**同一の8列**です。

| 列 | 内容 |
|---|---|
| `transaction_id` | ウォレット側の取引ID |
| `idempotency_key` | 貴社がお送りになった冪等キー |
| `external_user_id` | 貴社側のユーザーID |
| `amount` | 付与額 |
| `transaction_type` | `LEARNING_JOURNEY_REWARD` 等 |
| `rule_code` | `SENGOKU_LEARNING_JOURNEY_REWARD` 等 |
| `occurred_at` | 発生日時（ISO 8601・UTC） |
| `status` | `COMPLETED` 等 |

仕様上の制約は次のとおりです。

- **期間の上限は92日**です。これを超える範囲を指定されますと 400 を返します
- **1回の応答は最大10,000件**です。超過分を黙って切り捨てることはいたしません。
  応答ヘッダー `X-Has-More: true` と `X-Next-Cursor` で続きの有無をお知らせしますので、
  `X-Next-Cursor` の値をそのまま次回の `cursor` クエリパラメータへお渡しください。
  照合用APIですので、欠落が起きない作りにしてあります
- 返るのは**貴社ご自身が付与・利用された取引のみ**です。他社分は含まれません

### 1-2. 冪等キー単発照会（応答喪失時の復旧用）

```
GET /api/v1/service/transactions/by-idempotency-key/{idempotency_key}
```

「送信は成功したが応答を受け取れなかった」場合に、その取引がウォレット側で
成立しているかを確認していただく用途を想定しています。**再送前にこちらでご確認いただくと、
二重付与の心配なく判断できます**（冪等キーが同一であれば再送自体も安全ですが、
状態を先に確認できたほうが運用しやすいかと存じます）。

### 1-3. 弊社側でご利用前に必要な設定

この2本のAPIは**権限（scope）制御**がかかっており、既定では無権限です。
接続開始前に弊社側で以下を付与いたします。**貴社側の作業はございません。**

| scope | 対象API |
|---|---|
| `transactions.export` | 日次照合用CSV |
| `transactions.read` | 冪等キー単発照会 |

## 2. 【要ご確認】署名の作り方を変更しました

**貴社の実装着手前に、こちらだけお伝えさせてください。**

外部API（`X-OVE-*` ヘッダーを使う一連のAPI）の署名検証を、
**「実際に送信されたリクエストボディそのもの」に対して行う方式へ変更**いたしました
（2026-09-07 本番反映済み）。

### 何が変わったか

従来は、弊社側でボディを一度パースし、それを Node.js の `JSON.stringify` で
**組み立て直した文字列**を照合対象にしておりました。この方式ですと、貴社は
「ご自身が送信されたバイト列」ではなく「弊社の Node.js が再文字列化した結果」を
言い当てる必要があり、次のようなケースで**正しい署名なのに401になる**という
分かりにくい問題がございました。

- JSONのキーの順序が違う
- 整形（インデント・改行）を入れて送信している
- 日本語を `\uXXXX` にエスケープしている / していない
- ボディの無いGETで空文字に署名した（従来は `"{}"` が正解でした）

新方式では、**貴社に守っていただくのは次の1点だけ**になります。

> **ボディの文字列を1回だけ組み立て、その文字列に署名し、その同じ文字列を送信する。**

キーの順序・インデント・日本語のエスケープ方式は**どれでも構いません**。
弊社側で正規化や再整列は一切いたしません。

### 署名対象文字列

```
HMAC-SHA256(signing_secret, "<timestamp>.<nonce>.<METHOD>:<path>:<rawBody>")
```

- `timestamp` — **UNIXエポックのミリ秒（13桁）**。秒（10桁）ですと許容ずれ（±5分）を
  超えて401になります
- `path` — **クエリ文字列を含むフルパス**。エンコード済みの文字列をそのままお使いください
  （再エンコードなさらないでください）
- `rawBody` — **実際に送信されるボディの文字列そのもの**。
  **ボディの無いリクエスト（GET等）は空文字 `""`** です（`"{}"` ではありません）

### 実装例（Node.js）

要点は「`stringify` の結果を変数に取り、署名にも送信にも同じ値を使う」ことです。

```js
const rawBody = JSON.stringify(body); // ボディが無い場合は "" にする
const timestamp = String(Date.now());
const nonce = crypto.randomUUID();
const signature = crypto
  .createHmac("sha256", signingSecret)
  .update(`${timestamp}.${nonce}.${method}:${fullPath}:${rawBody}`)
  .digest("hex");

await fetch(`${baseUrl}${fullPath}`, {
  method,
  headers: {
    "Content-Type": "application/json",
    "X-OVE-Api-Key": apiKey,
    "X-OVE-Timestamp": timestamp,
    "X-OVE-Nonce": nonce,
    "X-OVE-Signature": signature,
  },
  body: rawBody || undefined, // ここで JSON.stringify(body) を書き直さないこと
});
```

### 契約テスト用の固定データをご用意しています

仕様書の読み合わせだけに頼らず機械的に検証していただけるよう、**12ケース分の
入力値と期待署名**を収録したファイルをご提供できます
（`docs/fixtures/hmac-auth-contract-fixtures.json`）。

各ケースには**実際に送信するボディ文字列が `rawBody` フィールドとして**入っておりますので、
それをそのまま署名して送っていただければ期待署名が再現されます。通常リクエスト・
クエリ文字列を含むパス・日本語ボディ・空ボディ・整形済みボディ・nonce再利用・
タイムスタンプ範囲外・署名不一致などを網羅しております。

このファイルは弊社側の実装と自動テストで継続的に突き合わせておりますので、
**実装と乖離することはありません。** 必要でしたらお送りいたします。

なお、**すでに接続いただいている他システムへの影響はございません。** 代理店システムは
HMAC署名を使わない方式、千ノ国マーケット様は別系統（共通イベント）で、
そちらはもともと生ボディ方式のためです。

## 3. ポイントの有効期限について → **弊社側の対応は不要でした**

「種類により期限のないものもある」旨、承知しました。

弊社の付与ルール（`reward_rules`）の有効期限設定は**もともと任意項目**で、
未設定であれば「**失効しない**」として扱う実装になっております。したがって
無期限のルールについて追加開発は発生いたしません。

期限を設けるルールと設けないルールを**同時に併存させることも可能**ですので、
ミッションの種類ごとに分けていただいて差し支えありません。

## 4. 付与ルールの登録について → **登録内容のご確認をお願いします**

「はじまりの旅」の付与は、**弊社側で付与ルールを登録しない限り通りません**
（`400 reward rule ... is not registered or not ACTIVE`）。

これは以前ご指摘いただいた「ルール未登録だと上限検証を素通りしてしまう」という
fail-open挙動への対応で、`LEARNING_JOURNEY_REWARD` を**明示的に fail-closed 側へ
登録**したためです。**上限のないまま付与が通ることはございません。**

つきましては、以下の内容で登録してよろしいかご確認ください。**この認識で相違なければ、
接続開始前に弊社側で登録いたします。**

| 項目 | 設定値 | 意味 |
|---|---|---|
| `rule_code` | `SENGOKU_LEARNING_JOURNEY_REWARD` | 照合CSVの `rule_code` 列に出る値 |
| `transaction_type` | `LEARNING_JOURNEY_REWARD` | 付与時にお送りいただく値 |
| `reward_amount` | 3,000 | 1回あたりの付与額 |
| `per_user_limit` | 1 | 1ユーザーにつき通算1回 |
| `per_event_limit` | 1 | 同一ミッション（`event_id`）につき1回 |
| `expiry_days` | 未設定（無期限） | 3章のとおり失効しません |

**特にご確認いただきたい点：**

- 金額 **3,000** で相違ございませんか
- 「1ユーザー通算1回」で正しいでしょうか。ミッションが複数あり**それぞれで付与**される
  設計でしたら、`per_user_limit` はミッション数に合わせるか、外していただく必要があります
  （`per_event_limit: 1` があれば同一ミッションの二重付与は防げます）
- 月間・全体の発行量上限を設けるご希望はございますか（任意設定です）
