# 外部ポイントからORIへの交換

2026-09-06実装。代理店システムなど**外部システムのポイント**を、利用者がORIへ交換できる
ようにする。

## 交換の操作は外部システム側で行う

利用者は**外部システムの画面**で交換操作をする。そちらでポイントを減らし、その分のORIを
`reward.granted` でウォレットへ送る。ウォレットは受けるだけになる。

ウォレット側に交換画面を作らないのは、**ポイント残高を持っている側で減算する方が確実**
だから。ウォレットから減算を依頼する形にすると、依頼と減算の間で二重交換が起こりうる。

**交換レートはウォレットが持たない。** 外部システムがレートを適用し、結果のORI数を
`amount` として送る。

## 受け口

```
POST https://api.sennokuni-wallet.com/api/integrations/events
event_type: reward.granted
```

会員券・NFTコレクションと**同じエンドポイント・同じ署名方式**。署名鍵の許可
`event_type` に `reward.granted` を足せば、新しい接続を作らずに済む。

`ENABLE_EXTERNAL_REWARD_TYPES` で開閉する。無効の間は受信しても記録のみで残高は動かない。

## 上限が素通りしないようにしている

**この経路は署名鍵さえあれば任意の額を発行できる。** 代理店の付与経路
(`/api/integrations/agencies/point-awards`) と違い、`service_integrations` の
1回あたり・日次の上限は**効かない** (認証が署名鍵で、連携先の行を引かないため)。

歯止めは `reward_rules` だけになる。ところが `COMMON_EVENT_REWARD` は既定で fail-open
で、**ルールが未登録なら上限検証を飛ばして付与を通す**。上限を「置いたつもり」で
素通りする状態になりうる。

そこで**この経路だけルールの登録を必須にした** (`requireRule`)。未登録・非ACTIVEなら
400で拒否する。

`transaction_type` 単位 (`REWARD_RULE_REQUIRED_TRANSACTION_TYPES`) で決め打ちにしなかった
のは、`COMMON_EVENT_REWARD` を代理店の付与経路と共有しており、そちらは既に本番で
稼働しているため。そこへ足すと、代理店側のルール未登録分まで止まってしまう。

**副次的な効果として、ルールを INACTIVE にすれば交換を止められる。** 管理画面から
即座に止まり、デプロイは要らない。

## rule_code は product_code から決まる

```
rule_code = "COMMON_EVENT_REWARD:" + (product_code ?? "default")
```

**外部システムが送る `product_code` と、登録する `rule_code` が一致していないと拒否
される。** 先方と値を決めてから登録すること。複数の商品・交換種別を扱うなら、
`product_code` ごとにルールを分ければ発行量も別々に集計される。

## 上限の考え方

| 上限 | 何を止めるか |
|---|---|
| `per_event_limit` | **桁の間違い**。レートの計算ミスで1回に大きな額が飛んでくるのを止める |
| `monthly_amount_limit` | **暴走**。同じ event_id の再送は元々二重付与しないので、暴走するとしたら別IDが大量に飛ぶ形になる。これは1回あたりの上限では止まらない |
| `per_user_limit` / `monthly_count_limit` / `global_amount_limit` | 必要なら追加で |

初期値は **1回あたり100,000 / 月あたり1,000,000** (2026-09-06 運用判断)。**最初は絞って
おき、実際の量を見てから上げる**方針。上限に当たると先方には400が返るので気づける。

累計 (`global_amount_limit`) は設定していない。永久の天井は忘れた頃に効いて原因が
分かりにくくなるため、月次で足りると判断した。

**上限は管理画面 `/reward-rules` から変更できる。デプロイは要らない。**

## 法令面の前提

交換元のポイントが**無償**であることを前提にしている (2026-09-06 確認)。ORIは
「無償で付与するサービス内ポイント、換金・送金不可」という整理で、資金決済法の
前払式支払手段には当たらないとしている (`/about` に明記)。

**交換元のポイントをお金で買えるようになると、ORIが間接的に「対価を得て発行」された
ことになりうる。** その時点で整理が変わるため、有償化の際は法務確認が要る。

## 取消

`reward.reversed` で戻せる。ただし**利用者が既にORIを使っていたら戻せない**
(現時点では使う導線が無いため問題にならない)。

## 動作確認

`apps/api/src/e2e/common-events.test.ts` — **付与ルールが未登録なら拒否すること**、
**ルールを止めれば付与も止まること**、付与と取消、冪等性、フラグ無効時に残高が動かないこと。

上限値そのものの検証は `common-events-p0.test.ts` (per_event_limit・
monthly_amount_limit を product_code 単位で効かせる) が既に行っている。

### 意図的に壊して確認

`requireRule` の判定を外したところ、上記2件が落ちた。

## 運用の手順

1. 先方と `product_code` を決める
2. 管理画面 `/reward-rules` で `COMMON_EVENT_REWARD:<product_code>` を登録し、上限を入れる
3. 管理画面「共通イベント署名鍵」で、その連携先の鍵の許可 `event_type` に
   `reward.granted` を含める
4. 先方へ鍵を渡す

止めたいときは、ルールを INACTIVE にする。
