# ポイント負債レポート

2026-08-31実装。発行済みで未使用のORI残高 (会計上の負債) を出すレポート。

導入前は、管理ダッシュボードに「今日の付与・利用」と過去30日の推移はあったが、
**現時点でいくら発行済みで未使用なのか**という会計上いちばん必要な数字を出す手段が
どこにも無かった。

## 負債の定義

```
負債残高 = SUM(wallets.available_balance + wallets.held_balance)
```

- **保留中 (`held_balance`) は含める。** 管理者が一時的に凍結しているだけで、
  利用者への債務は残っているため。
- **`pending_balance` / `recovery_balance` は含めない。** 台帳 (`packages/ledger/`) の
  どのコードパスからも書かれておらず常に0の未使用列のため。これらを使い始めるときは、
  この定義を見直すこと。

## 月次増減表 (ロールフォワード)

```
期首 + 発行 − 利用 − 失効 − 発行の取消 + 利用の取消 + その他増加 − その他減少 = 期末
```

増減の欄は**すべて0以上**にしてある。符号付きの純額にすると、CSVに負の数が出て
`common/csv.ts` のCSVインジェクション対策 (先頭が `-` の値に `'` を前置する) により
Excelで文字列扱いになり、合計が取れなくなるため。借方・貸方に分けて並べるのは
会計の増減表の書き方そのものでもある。

### 取引の分類

種別を列挙して分類するのではなく、**`direction` (CREDIT/DEBIT) を基準に**して例外だけを
名前で拾う。取引種別は今後も増えるため、列挙方式だと新しい種別がどの区分にも入らず、
合計だけが静かにずれるため。

| 区分 | 対象 |
|---|---|
| 発行 | CREDIT (下記の例外を除く) |
| 利用 | DEBIT (下記の例外を除く) |
| 失効 | `EXPIRATION` |
| 発行の取消 / 利用の取消 | `REVERSAL` (DEBIT側 / CREDIT側) |
| その他増加 / その他減少 | `BLOCKCHAIN_MIGRATION`・`MIGRATION_REVERSAL` (この台帳から負債が外に出る動きで、利用とは意味が違うため分ける) |

**集計対象外**:

- `HOLD` / `RELEASE`: available と held の間を移動するだけで合計は変わらない
- `ACCOUNT_MERGE_IN` / `ACCOUNT_MERGE_OUT`: ウォレット間の振替で全社合計では相殺される

どちらも増減表に載せると発行・利用の両方が実態より膨らむ。

### status の扱い

`COMPLETED` に加えて **`REVERSED` も集計対象に含める**。取消されると*元の取引*の
status が `REVERSED` に変わる (`packages/ledger/src/reversal.ts`) が、その取引は
発生時に確かに残高を動かしている。`COMPLETED` だけで絞ると、取消された付与が
「発行」から消える一方で取消の行だけが残り、増減の合計が実際の残高の動きと合わなくなる。
取消は取消日の別の行として計上されるため、二重計上にはならない。

`PENDING` / `FAILED` は残高を動かしていないので除く。

### 差異 (`discrepancy`)

`期首 + 増減` と `期末` のずれ。**0が正常**。0でなければ、台帳を経由しない残高変更が
あることを意味する (整合性チェック `AdminService.reconcile()` と同じ考え方の、期間版の
検算)。管理画面では0以外を赤字で表示する。

## 月末スナップショット

`point_liability_snapshots` に月末残高を1か月1行で保存する。会計が期首残高を出すのに
**全期間の取引を遡らずに済ませる**ため。

記録するのは「集計時点の実残高」ではなく**月末時点の残高**:

```
月末時点の残高 = 集計時点の実残高 − 月末以降の純増減
```

こうすることで、ジョブが月初に走っても数日遅れて走っても同じ値になる (過去月の後追い
記録にも使える)。取引 (`ove_transactions`) はDBトリガーで不変・追記のみなので、この
引き算は何度計算しても同じ結果になる。算出に使った実残高と差し引いた増減も
(`balance_at_capture` / `movement_after_period`) 残しており、監査時に計算を追える。

**一度記録した月は上書きしない。** 会計は締めた値が変わらないことを前提にするため。

定期実行は `liability-snapshot` ジョブ (毎月2日 09:00 JST、前月分が対象)。
JSTの月境界を確実に過ぎてから走らせている (値自体は実行時刻に依存しないので、
日付には余裕を持たせてある)。

## API

いずれも `SUPER_ADMIN` / `AUDITOR` のみ。全社の未使用残高は、個々の利用者の残高より
機微な経営情報のため、閲覧できるロールを絞っている。

| エンドポイント | 内容 |
|---|---|
| `GET /api/v1/admin/reports/point-liability` | 現時点の負債残高・内訳・失効見込み (30/60/90日) |
| `GET /api/v1/admin/reports/point-liability/roll-forward?months=N` | 月次増減表 (既定12か月、上限60) |
| `GET /api/v1/admin/reports/point-liability/roll-forward/export?months=N` | 同CSV |

## 画面

管理画面サイドバー「会計・レポート」→「ポイント負債レポート」
(`/reports/point-liability`)。上部に現時点の残高と失効見込み、下部に月次増減表。
CSVは画面の表示期間と同じ条件で出力する。

## 動作確認

`apps/api/src/e2e/point-liability.test.ts` (17件): 付与・利用による負債の増減、
保留が負債を変えないこと、増減表の各欄への振り分けと実際の残高の動きとの一致、
保留が増減表に載らないこと、増減の欄がすべて0以上であること、失効見込みの期間別集計、
スナップショットが月末時点の残高を記録すること (記録後の付与に影響されない)・二重に
記録しないこと・未終了の月を締められないこと、期首残高としての利用と検算、ずれた期首を
置いたときに差異として検知できること、ロール別の閲覧可否、CSVの形式。

全社集計のためテストDBの既存データが必ず混ざる。各テストは**変化量** (施行前後の差) を
見ることで、他のテストが作ったデータに影響されないようにしている。

## 今後の課題

- 経理から粒度の要望が出たら追加する (サービス別・付与ルール別の内訳など)。
  現状は全社合計のみ。
- スナップショットは残高だけを保存している。有効期限付きロットの月末残は過去に
  遡って正確に再構成できない (消費でロットの残が変わるため) ので、失効見込みは
  現時点の値のみを出している。
