# 運用手順: ENABLE_COMMON_USER_BALANCE_API の有効化・停止

対象: `POST /api/v1/service/accounts/by-common-user-id/balance`(PR-W2)

## Flagの反映条件

- `isFeatureEnabled()`(`apps/api/src/common/feature-flags.ts`)は`process.env`を毎リクエスト
  読み直すため、**同一プロセスが起動したまま**環境変数だけを書き換えても、そのプロセスの
  `process.env`自体は変わらない。反映には、新しい環境変数を読み込んだ状態でのプロセス起動
  (再起動または再デプロイ)が必要。
- 本リポジトリのRailwayデプロイ設定(`.github/workflows/deploy.yml`)は、変数を複数まとめて
  設定してから`railway up`で明示的に1回だけデプロイする構成になっており、個々の
  `railway variable set`呼び出しには`--skip-deploys`が明示的に付与されている。これは
  「`railway variable set`は既定で自動的に再デプロイを発生させる」ことを前提にした実装だと
  読み取れる(そうでなければ`--skip-deploys`を付ける意味がない)。これはコード上の状況証拠
  であり、Railwayダッシュボードから直接変数を編集した場合の挙動を本セッションから
  直接検証したものではない。**「変数を保存すれば即座に反映される」と断定しない**こと。
- したがって、正確な手順は「環境変数を変更する」→「(Railwayの自動再デプロイ、または
  手動でのサービス再起動によって)新しいプロセスが起動する」→「その新しいプロセスへの
  リクエストから反映される」の順であり、変更操作そのものが即時に反映を意味するわけではない。

## 反映確認の方法

変数を変更した後、以下のいずれかで実際に反映されたことを確認してから「完了」とする
(操作をしたこと自体を完了の根拠にしない):

1. `GET /api/v1/admin/feature-flags`(admin-wallet管理画面「外部連携キュー」ページ、
   または管理者セッションでの直接呼び出し)で`ENABLE_COMMON_USER_BALANCE_API`の値を確認する。
   このAPIも同じ`process.env`読み直し方式のため、実際に稼働中のプロセスの現在値を反映する。
2. 有効化を確認する場合: scope付与済みの検証用ServiceIntegrationで実際に
   `POST /api/v1/service/accounts/by-common-user-id/balance`を叩き、503ではなく
   200/400/404/409のいずれか(=Flagのゲートを通過している)が返ることを確認する。
3. 停止を確認する場合: 同じ呼び出しを行い、503(`FEATURE_DISABLED`)が返ることを確認する。

## 停止完了の判定

- 「Railwayで変数をfalseに変更した/削除した」時点ではなく、**上記2の確認方法で実際に
  503が返ることを確認した時点**を停止完了とする。
- 複数インスタンス構成の場合、変更直後は新旧のインスタンスが混在する可能性があるため、
  複数回(時間を空けて)確認することが望ましい。
