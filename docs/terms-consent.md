# 利用規約の同意・再同意

新規登録時の同意は以前から記録していたが、**現行バージョンと突き合わせる処理がどこにも
無く**、規約を改定しても既存利用者に同意を求める手段が無かった。2026-08-31に再同意の
仕組みを追加した。

## バージョンの持ち方

- 現行バージョン: `CURRENT_TERMS_VERSION` (`apps/api/src/accounts/account-registration.service.ts`)
- 利用者ごとの同意: `ove_accounts.terms_version` / `terms_agreed_at`

**規約を改定したら `CURRENT_TERMS_VERSION` を上げる。** それだけで、既存の全利用者が
次回の操作時に再同意を求められる状態になる。

## 再同意が必要と判定する条件

```
terms_version !== CURRENT_TERMS_VERSION
```

`terms_version` が **null のアカウントも対象に含める**。同意の記録を始める前に作られた
アカウントが該当するが、「記録が無い」と「同意していない」は区別できない以上、同意を
取り直す方が安全なため。

## API

| エンドポイント | 内容 |
|---|---|
| `GET /api/v1/accounts/me/terms` | 現行バージョン・同意済みバージョン・同意日時・`consent_required` |
| `POST /api/v1/accounts/me/terms/accept` | 現行バージョンへの同意を記録する |

```json
{
  "current_version": "1.0",
  "agreed_version": "0.9",
  "agreed_at": "2026-01-15T00:00:00.000Z",
  "consent_required": true
}
```

## 強制の仕方

再同意が必要な利用者の**更新系リクエスト (POST/PUT/PATCH/DELETE) を403で拒否**する。
**閲覧 (GET/HEAD/OPTIONS) は通す** — 残高が見えないと不安を招くだけで、同意を促す効果が
無いため。

判定は `SessionAuthGuard` で行う。個別のエンドポイントにデコレータを付ける方式にしないのは、
**後から追加された更新系エンドポイントが素通しになる**のを防ぐため (付け忘れても既定で
保護される)。

応答には機械可読コード `terms_consent_required` を `error` に載せる。フロントエンドは
英語のメッセージ文字列ではなくこれを見て再同意画面へ誘導する。

```json
{ "statusCode": 403, "error": "terms_consent_required", "message": "利用規約への同意が必要です。" }
```

## 再同意を求めない3つの出口

`@SkipTermsConsent()` を付けているのは次の3つだけ。**ここを広げると、規約に同意して
いない利用者がサービスを使い続けられてしまう。**

| エンドポイント | 理由 |
|---|---|
| `POST /accounts/me/terms/accept` | 同意そのもの。対象にすると同意できず詰む |
| `POST /auth/logout` | 同意しない利用者からログアウトの手段まで奪わない |
| `POST /accounts/me/close` | 同意しない利用者からサービスを離れる手段まで奪わない |

## 画面

`apps/user-wallet/src/components/TermsReconsentGate.tsx` を `/wallet` 配下のレイアウトに
挟み、同意するまでウォレットの画面を出さない。閲覧系APIは通るため画面自体は描けるが、
更新系がすべて403になるので「操作しようとするたびにエラーが出る」状態になってしまう。
先に同意を求めるほうが分かりやすい。

画面には**「同意せずログアウトする」も必ず出す**。同意を強いる形にしない。

未ログイン (401) の場合は関門を出さない。各ページ側が `/login` へ誘導するため、ここで
二重に遷移させるとちらつくため。

## 改定時の手順

1. `apps/user-wallet/src/app/terms/page.tsx` の本文とバージョン表記を更新する
2. `CURRENT_TERMS_VERSION` を上げる
3. デプロイする

デプロイ後、既存利用者は次に更新系の操作をしようとした時点 (実際にはウォレットを開いた
時点) で再同意画面に誘導される。**データ移行は不要**。

## 既知の制約

残高が残っている利用者は、退会に「残高0」が必要な一方で、残高を使う操作は更新系のため
再同意しないと実行できない。つまり**再同意せずに退会だけしたい利用者は、残高を使い切れ
ない**。規約改定時に残高の扱いをどうするかは、改定内容ごとに運用で判断すること
(暫定的に旧バージョンも有効として扱いたい場合は `CURRENT_TERMS_VERSION` を上げない、
という選択も取れる)。

## 動作確認

`apps/api/src/e2e/terms-reconsent.test.ts` (11件): 同意済み・旧バージョン・記録なしの
判定、更新系が403になり機械可読コードを返すこと、閲覧が通ること、同意済み利用者が
従来どおり操作できること、同意後に解除され記録が更新されること、3つの出口
(同意・ログアウト・退会) が拒否されないこと、未ログイン時の401。

既存の `apps/api/src/e2e/terms-consent.test.ts` (新規登録時の同意) は変更していない。
