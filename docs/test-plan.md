## 実施中に発見・修正した不具合 (実際に見つかったもの)

1. セッショントークンのハッシュ方式が検索キーとして機能しない設計ミス
2. HMAC署名シークレットを一方向ハッシュで保存していた設計ミス (検証不可能)
3. 外部API付与処理で、上限チェックがidempotencyチェックより先に走り、正当な再送が
   誤って拒否される不具合
4. 管理API (`GET /admin/wallets` 等) がPrismaのBigIntフィールドをJSONシリアライズできず
   500エラーになる不具合
5. 整合性チェック式で `REVERSED` 取引を除外していたため、取消のたびに残高が過大計上される不具合
6. 整合性チェック式で `RELEASE` 取引だけを合計に含め `HOLD` を除外し続けていたため、
   保留解除のたびに残高が過大計上される不具合
7. `monthly_count_limit`/`monthly_amount_limit` の集計をウォレット単位で行っていたため、
   別ユーザーへの付与では月間上限が実質的に機能しない不具合 (ルール単位/全ウォレット横断の
   集計へ修正)
8. `BigInt.prototype.toJSON` のパッチを `main.ts` のトップレベルにのみ書いていたため、
   `AppModule` を直接importするテスト (E2Eテストなど) ではパッチが効かず、BigIntフィールドを
   直接返すエンドポイント (外部サービス管理の一覧・緊急停止・再開など) が500エラーになる
   不具合。共有モジュール (`common/bigint-json.ts`) に切り出し、`main.ts` と `AppModule`
   の両方から読み込むよう修正
9. (テストコード自身のバグ) E2Eテストで管理者コードを `` `OVE-ADM-${generateId().slice(0, 8)}` ``
   のように生成していたが、ULIDの先頭8文字は主にタイムスタンプ部分でありランダム性がほぼ
   失われるため、近い時刻に生成された管理者コードが衝突し一意制約違反になっていた。
   スライスせず生成したIDをそのまま使うよう修正
10. 既存ユーザー移行のidempotencyKeyに `migration_batches.id` (実行のたびに新規生成される値)
    を含めていたため、同じCSVを再実行すると二重付与されてしまう不具合。CSV内容のSHA-256
    ハッシュ (実行のたびに変わらない値) を使うよう修正
11. (テストコード自身のバグ) `outbox.test.ts` で2つの`describe`ブロックがそれぞれ独立に
    `NestFactory.create(AppModule)`→`app.close()`を行っていたところ、`KeyValueStoreModule`の
    Redisクライアントがモジュールレベルの共有シングルトンであるため、先に閉じた側の
    `app.close()`がRedis接続自体を`quit()`してしまい、後段の`describe`が
    `Error: Connection is closed.`で管理者ログインに失敗していた。同一テストファイル内では
    Nest appを1つだけ生成し使い回すよう修正
12. メールOTP検証で、コードが未発行・期限切れの場合に`OtpVerificationError`が未捕捉のまま
    500エラーになる不具合。誤ったコードを入力した場合は401になっていたが、コード自体が
    存在しない場合だけ500になっていた。`rate-limit.test.ts`作成中(存在しないメールアドレスで
    OTP未発行のまま検証を試みるテストケース)に発覚。`AuthService.verifyEmailOtpAndLogin`で
    `OtpVerificationError`を捕捉し401に統一するよう修正
13. (フロントエンドのバグ) アカウント詳細画面で、REVIEWINGアカウントの検証結果反映に
    成功した直後、成功メッセージが一切表示されない不具合。成功メッセージの`<p>`を
    「`account.status === "REVIEWING"`の間だけ表示するセクション」の内側に置いていたため、
    解消に成功してstatusが`ACTIVE`に変わった瞬間、メッセージごとセクション全体が
    アンマウントされていた。実ブラウザ(Playwright)で確認結果テキストをアサートして
    初めて発覚 (見た目のスクリーンショットだけでは「成功はしている」ため気づきにくい)。
    メッセージ表示をそのセクションの外側に切り出し、status変化の影響を受けないよう修正
14. **(このセッション自身が生んだリグレッション)** `audit_logs`のDBレベル不変性トリガー
    (このドキュメントの11章、`add_audit_logs_immutability_trigger`) を追加した際、
    `packages/ledger`のテスト間クリーンアップ関数 `truncateLedgerTables()` が
    `prisma.auditLog.deleteMany()` を含んでいることを見落としていた。トリガー追加後、
    `packages/ledger`のテストは (他のテストスイートが作成した`audit_logs`行が
    削除できずトランザクション全体が失敗するため) 21件すべてが失敗する状態になっていたが、
    そのタスク完了時には`apps/api`のテストしか再実行しておらず、`packages/ledger`単体では
    再確認していなかったため見逃していた。今回、ルートの`pnpm test`(全ワークスペース横断)を
    初めて実行したことで発覚。`truncateLedgerTables()`から`auditLog.deleteMany()`を削除して
    修正 (各テストは`targetId`など固有の値で自分の監査ログを検索するため、他テストの残存行と
    衝突しない。監査ログを本当に削除しないのがこの機能の目的そのものでもある)。
    **教訓: DBスキーマ・トリガーレベルの変更を行った際は、そのタスクに直接関係する
    テストスイートだけでなく、ルートの`pnpm test`で全ワークスペースを横断的に
    再実行して確認すること。**

いずれも実際にAPIを呼び出して初めて発覚したものであり、修正後に自動テスト
(回帰テストを追加したものを含む) と手動確認の両方で解消を確認済み。

## 負荷・レート制限の限界値テスト (`tests/load`)

外部ツール(autocannon/k6等)を追加せず、Node組み込みの`fetch`のみで簡易負荷テストを実装した
(`tests/load/run.mjs`)。実行: `node tests/load/run.mjs` (apps/apiの起動が前提。
DATABASE_URL/REDIS_URLは起動済みのapps/apiと同じ対象に揃える必要がある)。

- `GET /health` に200並列リクエスト: 素の処理能力・レイテンシを計測。
- `GET /api/v1/me/wallet` (認証あり) に100並列リクエスト: 典型的な利用者トラフィックに近い
  経路でのレイテンシを計測。
- `POST /api/v1/admin/login` に30並列リクエスト: `rate-limit.test.ts` (逐次リクエストでの
  検証) とは異なり、**真の同時並行リクエスト**下でも `@nestjs/throttler` のカウントが
  正しく機能し (レースコンディションですり抜けが起きず)、設定した60秒10回の上限が
  厳密に守られることを確認する。

### 実施結果・発見した問題

初回実行で、`GET /health` への200並列リクエストのうち約4割(81件)が429 (Too Many Requests)
で拒否されることが判明した。ヘルスチェックエンドポイントに `@SkipThrottle()` が付いておらず、
通常のAPIトラフィックと同じ60秒120回の制限を共有していたため。ヘルスチェックはk8sの
liveness/readinessプローブやロードバランサから高頻度でポーリングされる想定であり、
これ自体が429を返すとオーケストレータがインスタンスを不健全と誤判定し再起動させてしまう
自己誘発的な障害になりかねない。`apps/api/src/health.controller.ts` に `@SkipThrottle()`
を追加して修正し、修正後は200並列リクエストが全件200 OKになることを確認した
(`docs/security.md` にも記載)。

管理者ログインのレート制限限界値テストでは、30並列リクエストのうち正確に10件が処理され

すり抜けは発生しなかった (真の同時実行下でもレースコンディションが無いことの裏付け)。
