## 手動E2E (実ブラウザ, Playwright, 実サーバー3本起動)

自動テストに加え、実際に `apps/api` (NestJS) / `apps/user-wallet` / `apps/admin-wallet` の
3サーバーを起動し、Playwrightでヘッドレスブラウザから操作して確認した:

- ユーザー: メールOTPログイン → ウォレットトップ表示 → 取引履歴ページ → OVEについてページ
- 管理者: ログイン → ダッシュボード (整合性チェック結果表示) → ウォレット一覧 →
  ウォレット詳細で個別付与を実行 → 反映確認 → 監査ログページ → CSV一括付与ページ →
  外部サービス管理画面で緊急停止/再開を実行 → 既存ユーザー移行画面でCSVを実行し
  正常/要確認の件数が画面に反映されることを確認 → アカウント統合画面で確認ダイアログ
  →実行し、移管残高が画面に表示されること・その後の残高整合性チェックが0件のままで
  あることを確認 → APIアクセスログ画面で、外部API経由の成功/認証失敗のログが表示され、
  ステータスコードによる絞り込みが機能することを確認 → アカウント一覧からアカウント詳細
  画面を開き、連携ID・外部サービス連携・操作ログが表示されること、統合済みアカウントでは
  統合先へのリンクと統合の操作ログが表示されることを確認 → セキュリティ設定画面でMFAを
  セットアップし、実際に生成したTOTPコードで有効化 → 一度ログアウトし、MFA必須の
  ログインで誤ったコードが日本語エラーメッセージ付きで拒否されること、正しいコードで
  ログインできることを確認 → 戦国ウォレットデザイン刷新後のログイン画面で、利用規約に
  同意せずログインを試みるとエラーになり、同意後は成功することを確認 → アカウント詳細画面で
  「全セッションを無効化」を実行し、アクティブセッション数が更新され、実際にユーザー側の
  セッションが即座に使えなくなることを確認 → LINEログイン後にウォレットホーム・取引履歴が
  新しい `/api/v1/me/*` API経由で表示されること、旧`/api/v1/wallets/{oveAccountId}/*`が
  404で応答しないことをブラウザから確認
- 外部API: HMAC署名付きリクエストで rewards/grant, transactions/debit, reverse を実行し、
  正しい署名は成功、リプレイは401、上限超過・重複はそれぞれ想定通りのレスポンスになることを
  curl/Pythonスクリプトで確認

## 実施中に発見・修正した不具合 (実際に見つかったもの)

1. セッショントークンのハッシュ方式が検索キーとして機能しない設計ミス
2. HMAC署名シークレットを一方向ハッシュで保存していた設計ミス (検証不可能)
3. 外部API付与処理で、上限チェックがidempotencyチェックより先に走り、正当な再送が
   誤って拒否される不具合
4. 管理API (`GET /admin/wallets` 等) がPrismaのBigIntフィールドをJSONシリアライズできず
   500エラーになる不具合
5. 整合性チェック式で `REVERSED` 取引を除外していたため、取消のたびに残高が過大計上される不具合
6. 整合性チェック式で `RELEASE` 取引だけを合計に含め `HOLD` を除外し続けていたため、
   保留解除のたびに残高が過大計上される不具合
7. `monthly_count_limit`/`monthly_amount_limit` の集計をウォレット単位で行っていたため、
   別ユーザーへの付与では月間上限が実質的に機能しない不具合 (ルール単位/全ウォレット横断の
   集計へ修正)
8. `BigInt.prototype.toJSON` のパッチを `main.ts` のトップレベルにのみ書いていたため、
   `AppModule` を直接importするテスト (E2Eテストなど) ではパッチが効かず、BigIntフィールドを
   直接返すエンドポイント (外部サービス管理の一覧・緊急停止・再開など) が500エラーになる
   不具合。共有モジュール (`common/bigint-json.ts`) に切り出し、`main.ts` と `AppModule`
   の両方から読み込むよう修正
9. (テストコード自身のバグ) E2Eテストで管理者コードを `` `OVE-ADM-${generateId().slice(0, 8)}` ``
   のように生成していたが、ULIDの先頭8文字は主にタイムスタンプ部分でありランダム性がほぼ
   失われるため、近い時刻に生成された管理者コードが衝突し一意制約違反になっていた。
   スライスせず生成したIDをそのまま使うよう修正
10. 既存ユーザー移行のidempotencyKeyに `migration_batches.id` (実行のたびに新規生成される値)
    を含めていたため、同じCSVを再実行すると二重付与されてしまう不具合。CSV内容のSHA-256
    ハッシュ (実行のたびに変わらない値) を使うよう修正

いずれも実際にAPIを呼び出して初めて発覚したものであり、修正後に自動テスト
(回帰テストを追加したものを含む) と手動確認の両方で解消を確認済み。
